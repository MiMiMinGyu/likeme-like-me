# [LikemeLikeMe] 회고 - 모델 선정부터 AWS 배포까지, 다시 열어 본 프로젝트

## 배경

LikemeLikeMe는 캡스톤디자인2 수업에서 팀원들과 만든, 사용자의 말투를 참고해 답장을 만들어 주는 AI 서비스다. 프로젝트 소개는 [README](../../README.md)에 기록해 두었다.

캡스톤이 끝난 뒤 이 프로젝트를 혼자 다시 열어 Docker로 묶고, Docker Compose로 엮은 뒤 AWS에 올렸다. 증거를 남긴 뒤에는 서버를 철거했다. 그 과정에서 겪은 문제 가운데 세 가지는 따로 글로 썼다.

- [깨끗한 DB에서 만난 Prisma 마이그레이션 오류](01-migration-replay.md)
- [Caddy 라우팅과 브라우저 캐시](02-caddy-routing-cache.md)
- [SSH 타임아웃에서 SSM Session Manager 전환까지](03-ssh-to-ssm.md)

캡스톤 때는 인프라를 구성하고 배포하는 데까지 가지 못했다. 이번에 그 부분을 다시 만들어 보면서, 당시에 더 잘할 수 있었던 것들이 눈에 들어왔다. 이 글은 그 연재의 마무리로, 문제 하나를 따라가는 대신 캡스톤 때와 이번 재배포를 나란히 놓고 되짚어 본다. 앞선 글을 읽지 않아도 이해할 수 있게 쓰되, 자세한 내용은 위 링크에 있다.

## 캡스톤에서는 모델을 먼저 정했다

2025년 2학기 캡스톤에서 우리는 오픈소스 LLM인 `llama-3.2-Korean-Bllossom-3B`를 먼저 정해 두고 시작했다. AI 파트가 회의에서 이 모델을 공유했고, 그대로 시작하기로 했다. 당시 모델 선정 기준은 네 가지였다.

1. 목표가 채팅 말투를 닮게 하는 것이라서 한국어 모델일 것
2. 비용 때문에 파라미터 수가 3B 이하일 것
3. 학술적으로 이용할 수 있는 모델일 것
4. 다운로드 수가 1k 이상일 것. 다운로드 수를 신뢰도의 기준으로 보았다.

이 모델을 AI Hub 데이터와 드라마 대본 등으로 전처리해 학습시켰다. 데이터에 다양한 말투와 특징이 담겨 있으면 모델이 그것들을 익혀 활용할 수 있을 것이라고 생각했다. 그렇게 말투를 익힌 모델에 사용자의 카카오톡 대화(txt)를 DB로 더해, 개인의 말투에 맞는 응답을 만드는 것이 계획이었다.

결과는 기대와 달랐다. 모델이 학습한 것은 말투가 아니라 대화 내용에 가까웠고, 응답의 말투는 모델 고유의 말투에 머물렀다. FAISS와 RAG까지 시도한 끝에, 완성된 GPT 모델에 RAG를 붙인 구성으로 마무리했다.

되돌아보면 이 네 가지 기준에는 준비한 데이터의 규모나, 학습한 뒤의 결과를 가늠해 보는 항목이 없었다. 모델이 목표에 맞는지는 따졌지만, 데이터로 말투를 익힐 수 있다는 가정이 맞는지는 시작하기 전에 확인하지 못했다.

## 지금 다시 보니 달랐을 것

모델을 먼저 정한 것 자체는 문제가 아니었다고 생각한다. 문제는 그 과정이었다. 우리는 배경 정보 없이, 당시 아는 범위에서 세운 기준을 필터로 삼아 모델을 골랐다. 그중 하나가 파라미터 수를 3B 이하로 제한한다는 기준이었다. 모델이 클수록 서빙에 더 많은 인스턴스가 필요하고 비용도 커지기 때문에, 배포까지 염두에 두고 정한 기준이었다. 다만 학습한 모델을 실제로 어떻게 서빙할지는 알지 못한 채 정한 것이었다. 반면 1년쯤 뒤 진행한 다른 프로젝트인 true-education에서는 멘토링에서 클라우드 GPU 인스턴스의 비용이 부담이라는 이야기를 듣고, Tailscale로 로컬 PC의 LLM과 AWS 서버를 사설망으로 연결해 GPU 인스턴스 없이 배포했다([true-education-backend](https://github.com/MiMiMinGyu/true-education-backend)). 같은 비용 문제를 다른 방식으로 푼 셈이다. 다만 그때도 실제 금액이나 성능은 비교해 보지 않았다. 캡스톤 때 이런 방법을 알았다면 이 기준도 달라졌을 수 있다.

프로젝트가 후반으로 접어들 무렵 전처리한 데이터 일부를 모델에 학습시켜 성능을 시험해 보았다. 성능은 기대에 한참 못 미쳤고, 데이터가 부족한 탓인가 싶어 사용할 데이터를 거의 다 학습시켜 보았지만 모델은 말투를 익히지 못했다. 그제야 서둘러 대책을 찾다가 RAG, 벡터 DB 같은 기법을 알게 되었고, 결국 GPT-4o mini에 RAG를 붙인 구성으로 방향을 바꿨다.

돌이켜 보면 만들려는 것에 비해 준비가 많이 부족했다. 당시에는 "LLM은 학습시키기 나름이지 않을까"라는 막연한 기대가 컸고, 모델이 프로젝트의 가장 큰 걸림돌이 될 것이라고는 예상하지 못했다. 벤치마크와 예산, 데이터의 규모와 품질을 함께 보고 골랐다면, 이런 기법을 계획 단계에서 알았다면, 이른 시기부터 확인 지점을 반복해서 두었다면 모델과 기술 스택을 더 일찍 정할 수 있지 않았을까 싶다.

모델 선정과 기술 스택을 체계화하는 것보다 더 아쉬웠던 것은 협업이다. 4명이 함께한 프로젝트였지만 나는 풀스택으로 내가 해야 할 일을 처리하기에 급급했고, 필요할 때 리더십을 발휘하기보다 팔로워십에 머물렀다. 작업을 나누어 넘기고 검토하는 것보다 내가 구조를 잡아 직접 만드는 편이 낫겠다는 생각이 앞섰다. 그러다 보니 모두가 같은 기준으로 같은 결과를 낼 수 있게 하는 일은 하지 못했다. 팀원마다 지식과 LLM을 쓰는 방식이 달랐는데, 지금 생각해 보면 이를 맞추는 규칙과 구조를 초기에 먼저 확립해 두었어야 했다. true-education에서는 회의록과 API 명세를 문서로 고정하고 각자의 AI가 작업 전에 이를 먼저 읽게 하는 [하네스 엔지니어링](https://github.com/MiMiMinGyu/true-education-backend/blob/main/docs/blog/02-harness-engineering.md)을 시도했고, 그 프로젝트는 대회에서 대상을 받았다. 수상이 하네스 덕분이라고 단정할 수는 없지만, 팀이 같은 기준으로 움직이는 데에는 도움이 되었다고 느꼈다.

위에서 말한 것들은 지금의 생각일 뿐, 실제로 그렇게 했다면 결과가 달라졌을지는 알 수 없다. 어디까지나 개인적인 아쉬움이다.

## 다시 만들며 가려져 있던 것

이번에 인프라를 직접 만들어 보니, 캡스톤디자인2 수업 당시에 배포를 시도했더라도 쉽지 않았을 것이라는 생각이 든다. 그때 배포를 이렇게 했어야 했다는 아쉬움은 크지 않다. 대신 로컬에서는 보이지 않던 것이 배포 단계에서 드러난다는 것을 이번에 직접 겪었다.

앞선 세 글이 그 사례다.

- 마이그레이션은 로컬 DB에서는 이미 지나온 길이라 매번 통과했지만, 빈 DB에서 처음부터 적용하자 네 번째에서 실패했다. 로컬에서 "돌아간다"와 처음부터 "돌아간다"는 다른 문제였다.
- 로컬에서 확인한 범위(로그인, 추천 답변, 카카오톡 업로드) 밖에 있던 관계 표시 화면이 배포에서 처음 깨졌다. 원인은 Caddy의 경로 매칭 규칙과 브라우저 캐시였다.
- 로컬에서는 서버에 접속할 일이 없었지만, 배포하자 접속 방식도 설계해야 했다. 접속하는 노트북의 위치가 바뀌면 22번 포트에 걸어 둔 IP 제한이 맞지 않게 되어, SSH에서 SSM으로 접속 방식을 바꾸게 되었다.

글로 쓰지 않은 개선도 두 가지 있었다. 먼저 ECR 기본 스캔에서 api 이미지는 중요(Critical) 6건과 높음(High) 21건이 나왔다. 베이스 이미지를 같은 태그의 최신 버전으로 갱신하자 중요 0건, 높음 6건으로 줄었고, 기능과 이미지 크기는 그대로였다. 남은 건 베이스 OS 패키지에서 나온 것이어서 이번에는 고치지 않았다. 다음으로, 로그인 없이 호출할 수 있던 `/telegram` 일부 엔드포인트에 인증 가드를 추가해 비로그인 요청이 `401`을 받도록 했다.

만드는 것만큼 지우는 것도 일이었다. 서버를 `terraform destroy`로 한 번에 내리고, 도메인 레코드와 파라미터 저장소의 값, 액세스 키를 정리했고, IAM 권한은 ECR 삭제에 필요한 것만 남겼다. 마지막으로 ECR을 지운 뒤 나머지 권한을 회수할 것이다. 실제 청구액은 Cost Explorer로 확인한 뒤 기록하려 한다.

## 같은 패턴

캡스톤 때와 이번 재배포를 나란히 놓으면 닮은 점이 하나 보인다. 둘 다 가정을 먼저 세우고, 그 가정을 확인하는 일은 뒤로 미뤘다.

달랐던 것은 확인이 늦은 대가였다. 캡스톤에서는 "데이터에 다양한 말투가 담겨 있으면 모델이 말투를 익힐 것"이라는 가정을 프로젝트가 후반으로 접어들 무렵 학습시켜 본 뒤에야 확인했고, 그 대가는 이어 오던 방향을 바꾸는 것이었다. 이번에는 같은 와이파이면 접속에 문제가 없을 것이라는 가정이 한 시간 만에 깨졌고, 로컬에서 돌아가니 새 환경에서도 돌아갈 것이라는 가정은 빈 DB에서 네 번째 마이그레이션이 실패하면서 깨졌다. 둘 다 곧바로 원인을 찾아 고칠 수 있었다. 확인이 늦었다는 점은 같은데, 인프라를 코드로 만들고 임시 DB를 쓸 수 있는 환경에서는 틀린 가정으로 치르는 대가가 훨씬 적었다.

반대로 확인을 앞에 둔 경우도 있었다. SSM으로 접속 방식을 바꿀 때 22번을 먼저 닫지 않고, 새 방식이 되는지부터 확인한 뒤 마지막에 닫았다. 가정이 틀려도 되돌아올 길을 남겨 두는 방식이었고, 실제로 SSM 연결이 되지 않았을 때 22번 덕분에 서버에 들어가 원인을 확인할 수 있었다.

앞으로는 무언가를 시작하기 전에 두 가지를 먼저 적어 두려 한다. 이 가정이 틀리면 무엇이 깨지는지, 그리고 그것을 가장 적은 비용으로 확인하는 방법은 무엇인지다. 캡스톤 때 이 질문을 했다면 학습 데이터를 더 모으기 전에 작게 한 번 학습시켜 보는 방법을 더 일찍 떠올렸을지도 모른다.

## 마무리

이번 재배포는 서버 한 대에 컨테이너 네 개(web, api, embedding, db)를 올린 구성이다. 실제 서비스를 운영하는 수준은 아니어서, 여러 서버로의 확장이나 자동 복구, 무중단 배포는 다루지 않았다.

이번에 고치지 않고 남긴 것도 있다. `messageId`가 요청자의 대화에 속하는지 확인하는 객체 수준 권한 검사는 아직 없고, 이미지 스캔에 남은 베이스 OS 패키지의 취약점도 그대로다. SSM 권한은 AWS 관리형 정책을 그대로 쓰고 있어 필요한 권한만 담은 정책으로 줄이는 것이 남았고, 빈 DB에서 마이그레이션을 처음부터 적용해 보는 확인을 자동으로 돌려 주는 CI도 없다. 전체 목록은 [REFACTORING_LOG](../REFACTORING_LOG.md)에 정리해 두었다.

캡스톤 때 하지 못한 인프라 구성과 배포를 이번에 직접 해 보니, 문제 가운데 상당수는 확인하지 않은 가정에서 나왔다. 다음 프로젝트에서는 시작하기 전에 가정이 틀리면 무엇이 깨지는지, 그것을 가장 적은 비용으로 확인하는 방법이 무엇인지부터 적어 두려 한다.
